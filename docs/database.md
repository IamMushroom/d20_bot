# Модуль базы данных

Модуль `src/database` хранит данные кампаний, персонажей, игровых сессий и рекапов. Сейчас поддерживается только SQLite, однако команды и репозитории зависят от интерфейса `Database`, а не от `sqlite3.Connection`. Это оставляет возможность заменить реализацию подключения без изменения пользовательской логики.

## Структура

```text
src/database/
├── __init__.py                 # публичные объекты модуля
├── connection.py               # Database, SQLiteDatabase и фабрика
├── migrations.py               # применение SQL-миграций
├── models.py                   # неизменяемые модели данных
└── repositories/
    ├── campaigns.py
    ├── characters.py
    ├── sessions.py
    ├── game_configs.py
    └── recaps.py

migrations/
├── 001_initial_schema.sql
├── 002_game_schedule.sql
├── 003_game_config.sql
└── 004_unify_schedules_and_sessions.sql
```

Telegram-команды не должны выполнять SQL напрямую. Ожидаемый поток зависимостей:

```text
Telegram command → service/repository → Database → SQLite
```

## Конфигурация

Подключение задаётся переменной окружения `DATABASE_URL`:

```dotenv
DATABASE_URL=sqlite:////data/d20.sqlite3
```

Четыре косые черты обозначают абсолютный путь `/data/d20.sqlite3`. Для относительного локального пути используется:

```dotenv
DATABASE_URL=sqlite:///data/d20.sqlite3
```

Для тестов доступна база в памяти:

```text
sqlite:///:memory:
```

Другие схемы URL сейчас отклоняются с `ValueError`. Добавление нового backend начинается с реализации протокола `Database` и новой ветки в `create_database()`.

## Интерфейс подключения

`Database` определяет минимальный асинхронный контракт:

```python
class Database(Protocol):
    async def execute(self, query, parameters=()) -> int: ...
    async def fetch_one(self, query, parameters=()) -> Row | None: ...
    async def fetch_all(self, query, parameters=()) -> list[Row]: ...
    async def executescript(self, script) -> None: ...
    async def close(self) -> None: ...
```

- `execute()` выполняет запрос и возвращает число изменённых строк.
- `fetch_one()` возвращает одну строку как `Mapping` либо `None`.
- `fetch_all()` возвращает список строк.
- `executescript()` предназначен прежде всего для миграций.
- `close()` закрывает подключение.

Запросы всегда должны использовать параметры `?`, а не интерполяцию пользовательских данных:

```python
row = await database.fetch_one(
    'SELECT * FROM campaigns WHERE chat_id = ?',
    (chat_id,),
)
```

## Реализация SQLite

`SQLiteDatabase` использует стандартный модуль `sqlite3`. Блокирующие операции выполняются через `asyncio.to_thread()`, поэтому они не блокируют event loop Telegram-бота.

Все операции одного экземпляра сериализуются через `asyncio.Lock`. Это защищает общее соединение от одновременного использования внутри процесса.

При подключении включаются:

```sql
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA journal_mode = WAL;
```

- `foreign_keys` включает проверку внешних ключей.
- `busy_timeout` позволяет подождать освобождения занятой базы до пяти секунд.
- WAL улучшает совместную работу чтения и записи и упрощает создание резервных копий.

Соединение работает в режиме autocommit. Атомарные операции репозиториев поэтому оформляются одним SQL-запросом. Если будущая операция требует нескольких связанных запросов, сначала следует расширить интерфейс явной поддержкой транзакций.

## Lifecycle приложения

База подключается в `initialize_application()` до регистрации команд Telegram:

1. Читается `DATABASE_URL`.
2. Создаётся подключение.
3. Применяются миграции.
4. Подключение сохраняется в `application.bot_data['database']`.
5. Регистрируются команды бота.

Если миграция завершается ошибкой, подключение закрывается, а запуск приложения прекращается. При штатной остановке `shutdown_application()` извлекает базу из `bot_data` и закрывает её.

Получение базы из обработчика команды:

```python
from database import Database

database: Database = context.application.bot_data['database']
```

## Миграции

Миграции находятся в корневом каталоге `migrations` и называются по шаблону:

```text
NNN_description.sql
```

Примеры:

```text
001_initial_schema.sql
002_add_recap_title.sql
```

Версия состоит ровно из трёх цифр. Файл с неправильным именем или повторяющейся версией останавливает запуск.

Применённые версии записываются в служебную таблицу:

```sql
schema_migrations(version, applied_at)
```

Каждая новая миграция выполняется внутри `BEGIN IMMEDIATE ... COMMIT`. Повторный запуск безопасен: уже зарегистрированные версии пропускаются.

Правила добавления миграций:

1. Не изменять миграции, уже применённые в окружениях.
2. Создавать новый файл со следующим номером.
3. Не добавлять вручную запись в `schema_migrations`.
4. Не добавлять в файл `BEGIN`, `COMMIT` или `ROLLBACK` — ими управляет runner.
5. Проверять миграцию как на пустой базе, так и на базе предыдущей версии.

Миграции копируются и в test-, и в runtime-слой Docker-образа.

## Модель данных

### Campaign

Кампания соответствует Telegram-чату.

| Поле | Назначение |
|---|---|
| `id` | Внутренний идентификатор |
| `chat_id` | Уникальный Telegram chat ID |
| `title` | Название кампании или чата |
| `created_at` | Время создания в UTC |

### Character

Персонаж принадлежит кампании и Telegram-пользователю. Один пользователь может иметь по одному зарегистрированному персонажу в каждой кампании.

Уникальность обеспечивается парой `(campaign_id, telegram_user_id)`.

### Session

Игровая сессия получает последовательный номер внутри кампании и является единым
источником данных как для расписания, так и для истории игр.

- planned: заполнено `scheduled_at`, `started_at` отсутствует;
- active: заполнено `started_at`, `finished_at` отсутствует;
- finished: заполнено `finished_at`.

Поля `foundry_url` и `message_id` относятся к объявлению planned-сессии. Частичные
уникальные индексы разрешают только одну planned и одну active-сессию на кампанию.

### RecapEntry

Фрагмент рекапа связан с сессией и персонажем. Поле `position` задаёт порядок фрагментов внутри сессии и уникально в пределах этой сессии.

Все временные значения записываются в UTC в формате ISO 8601 и преобразуются репозиториями в `datetime`.

## Репозитории

### CampaignRepository

```python
campaign = await CampaignRepository(database).get_or_create(
    chat_id=-100123456,
    title='Проклятие Страда',
)
```

- `get_or_create(chat_id, title)` создаёт кампанию или возвращает существующую. Переданный непустой `title` обновляет название.
- `get_by_chat_id(chat_id)` ищет кампанию по Telegram chat ID.

### CharacterRepository

```python
character = await CharacterRepository(database).register(
    campaign_id=campaign.id,
    user_id=telegram_user_id,
    name='Тилли Клык',
)
```

- `register()` создаёт персонажа или обновляет имя уже зарегистрированного.
- `get_by_user()` возвращает персонажа пользователя в указанной кампании.

### SessionRepository

```python
sessions = SessionRepository(database)
planned = await sessions.schedule(campaign.id, scheduled_at, foundry_url)
session = await sessions.start(campaign.id, 'Старая башня')
await sessions.finish(session.id)
```

- `schedule()` создаёт planned-сессию или переносит уже существующую.
- `get_planned()` получает ближайшую запланированную сессию кампании.
- `set_message_id()` связывает сессию с Telegram-объявлением.
- `start()` переводит planned-сессию в active; если плана нет, создаёт новую active-сессию.
- `finish()` завершает активную сессию; повторное завершение возвращает `None`.
- `get_active()` получает открытую сессию кампании.
- `get_latest()` получает последнюю сессию независимо от её состояния.
- `list()` возвращает сессии в порядке номеров.

Попытка открыть вторую active-сессию приводит к `sqlite3.IntegrityError`. Пользовательский слой должен преобразовать её в понятный ответ Telegram.

Миграция `004_unify_schedules_and_sessions.sql` переносит строки старой таблицы
`game_schedules` в planned-сессии, сохраняя дату, Foundry URL и Telegram message ID,
после чего удаляет старую таблицу. Существующие сессии и связанные рекапы сохраняются.

### RecapRepository

```python
recaps = RecapRepository(database)
entry = await recaps.add(session.id, character.id, 'Мы вошли в башню.')
entries = await recaps.list_by_session(session.id)
```

- `add()` сохраняет фрагмент и назначает следующую позицию.
- `list_by_session()` возвращает фрагменты в порядке написания.
- `delete_last()` удаляет последний фрагмент указанного персонажа и сообщает, была ли строка удалена.

## Docker и хранение данных

Compose подключает именованный volume:

```yaml
volumes:
  - d20-data:/data
```

Он необходим, поскольку корневая файловая система контейнера работает в режиме `read_only`. Пересоздание контейнера не удаляет данные из volume.

Dev и production запускаются с разными Compose project names, поэтому получают разные физические volumes. Удаление через `docker compose down` сохраняет базу; `docker compose down --volumes` удаляет её безвозвратно.

Для согласованного резервного копирования следует использовать SQLite backup API или команду `.backup`. Не рекомендуется копировать только основной `.sqlite3`-файл во время работы приложения: часть данных может находиться в WAL-файле.

## Тестирование

Интеграционные тесты находятся в `tests/test_database.py`. Каждый сценарий использует отдельную базу из `tmp_path` или `:memory:`.

Проверяются:

- фабрика подключений;
- повторное применение миграций;
- валидация имён миграций;
- полный lifecycle кампании, персонажа, сессии и рекапа;
- порядок фрагментов;
- запрет нескольких активных сессий;
- создание, перенос и запуск planned-сессии;
- перенос существующего расписания в `sessions` без потери рекапов;
- инициализация и закрытие базы вместе с приложением.

Запуск:

```shell
uv run pytest
```

Из-за общего порога coverage не следует запускать только `test_database.py` без изменения параметров pytest: отдельный файл не покрывает остальные модули приложения.

## Добавление другой СУБД

Подготовленный интерфейс — страховка, а не обещание полной переносимости текущего SQL. Репозитории сейчас используют SQLite-синтаксис `?`, `ON CONFLICT`, `RETURNING` и частичный индекс.

Для нового backend потребуется:

1. Реализовать методы `Database`.
2. Добавить обработку новой схемы URL в `create_database()`.
3. Подготовить отдельный набор миграций.
4. Реализовать репозитории с SQL нового диалекта либо вынести общий слой запросов.
5. Прогнать единый контракт интеграционных тестов для обеих реализаций.

До появления реальной необходимости SQLite остаётся единственной поддерживаемой СУБД.
